# AutoVul rename plan

This plan implements `rename-project-to-autovul` after explicit acceptance. It does not authorize implementation while the change SPEC remains Draft.

## Baseline

The former name currently appears in:

- root package metadata and package lock;
- five private workspace package names and their imports;
- the CLI binary and README examples;
- Pi UI, lifecycle strings, prompts and help;
- application and Golden environment variables;
- generated qlpack names, CodeQL rule ids and provenance;
- temporary directories, LSP client names and test fixtures;
- accepted and historical specifications.

The worktree also contains workflow commit-hardening changes. Rename implementation must not be mixed into an unstable persistence checkpoint.

## Target state

```text
Brand:       AutoVul
Packages:    @autovul/contracts
             @autovul/core
             @autovul/codeql-runner
             @autovul/pi-extension
             @autovul/cli
CLI:         autovul
Compat CLI:  pure-auto-codeql-v2
Environment: AUTOVUL_*
Compat env:  PURE_AUTO_CODEQL_*
```

CodeQL-specific tools and commands retain their existing names. Historical rule ids and artifacts remain valid.

## Checkpoint 0: Accept and freeze the migration map

Work:

- Review and accept the change SPEC.
- Record the complete old-to-new environment-variable map.
- Confirm the private `@autovul/*` workspace namespace.
- Establish the exact historical/compatibility allowlist for old-name occurrences.
- Choose a stable workflow-hardening checkpoint as the rename base.

Exit criteria:

- change SPEC status is Accepted;
- no package, CLI, environment or artifact choice remains ambiguous;
- the persistence-hardening work is independently reviewable.

## Checkpoint 1: Current documentation and project charter

Likely files:

- `README.md`
- `AGENTS.md`
- `CLAUDE.md`
- root `SPEC.md`
- `docs/design/FLOW_BASED_DIRECTION.md`
- issue and contribution templates where applicable.

Work:

- Replace current human-facing branding with AutoVul.
- Preserve the non-Agent host boundary verbatim in meaning.
- Keep historical change documents accurate and add rename notes only where needed.
- Update examples to prefer the canonical CLI and environment names after those entries exist.

Exit criteria:

- current documentation consistently presents AutoVul;
- no new capability claim appears;
- historical records remain traceable.

## Checkpoint 2: Workspace package namespace

Likely files:

- root and workspace `package.json` files;
- first-party TypeScript and JavaScript imports;
- dependency and package-output checks;
- `package-lock.json` regenerated by npm.

Work:

- Rename private packages to `@autovul/*` in one buildable checkpoint.
- Update all first-party imports and workspace dependencies.
- Update pack and architecture checks.
- Regenerate the lockfile without upgrading unrelated dependencies.
- Run a clean build to ensure no former package output remains.

Exit criteria:

- clean install/build resolves only canonical workspace packages;
- dependency direction remains unchanged;
- package output contains no stale former workspace package.

## Checkpoint 3: CLI and environment compatibility

Likely files:

- `packages/cli/package.json`
- CLI and application construction modules;
- Pi extension construction;
- environment-focused tests and README examples.

Work:

- Add `autovul` as the canonical binary.
- Keep `pure-auto-codeql-v2` mapped to the same entry point.
- Introduce one typed environment compatibility resolver.
- Add canonical `AUTOVUL_*` names and old-name fallbacks.
- Make canonical values win when both are present.
- Avoid printing configuration values or secrets in deprecation diagnostics.

Exit criteria:

- both CLI names pass the same integration suite;
- new, old and conflicting environment cases are tested;
- current documentation uses only canonical names except the migration section.

## Checkpoint 4: Pi integration and runtime display names

Likely files:

- `packages/pi-extension/src/`
- LSP client metadata;
- temporary workspace prefixes;
- runtime display and lifecycle tests.

Work:

- Rename project display text and internal first-party function identifiers.
- Move the UI key to `autovul` with reload/cleanup compatibility.
- Preserve CodeQL tool and command names.
- Rename LSP client display names and temporary paths where they are non-semantic.
- Preserve process cleanup and trusted-root behavior.

Exit criteria:

- Pi RPC smoke registers the same CodeQL capability surface;
- UI presents AutoVul and cleans stale state;
- LSP conformance remains unchanged.

## Checkpoint 5: Artifact and rule-identity compatibility

Likely files:

- language packs and Python renderer;
- Query Pack finalization;
- Golden manifests and replay tests;
- provenance and qlpack generation.

Work:

- Classify each embedded old name as stable identity, compatibility fixture or replaceable display branding.
- Preserve stable CodeQL rule ids for semantically unchanged rules.
- Use AutoVul for new provenance display strings and non-semantic generated qlpack names.
- Test loading and replaying pre-rename artifacts.
- Ensure new readers accept both brands without weakening schema validation.

Exit criteria:

- old and new Query Packs replay;
- unchanged rules retain stable SARIF identity;
- no artifact is rewritten in place;
- Golden differential results remain unchanged.

## Checkpoint 6: Naming governance

Likely files:

- a repository naming-check script;
- root npm scripts;
- explicit compatibility allowlist.

Work:

- Scan current source, docs, package metadata and generated package file lists.
- Reject unapproved former-brand occurrences.
- Allow only named compatibility aliases, historical records, legacy fixtures and stable rule ids.
- Report the file, line and allowlist category for every permitted occurrence.

Exit criteria:

- accidental old branding fails CI;
- compatibility and history remain explicit rather than hidden by directory exclusions.

## Checkpoint 7: Full verification

Commands:

```bash
npm install --package-lock-only --ignore-scripts
npm run check
npm run test:e2e
npm run test:lsp:conformance
npm run test:m3-golden-real
git diff --check
```

Additional checks:

- canonical and compatibility CLI entries;
- environment migration matrix;
- old-run fixture load;
- pre-rename and post-rename Query Pack replay;
- clean package file-list inspection;
- naming allowlist report.

Exit criteria:

- every MUST requirement has mapped evidence;
- no skipped check is reported as success;
- the rename change reaches Verified;
- stable AutoVul naming is merged into root `SPEC.md` before Archived.

## Recommended review sequence

1. SPEC and migration map;
2. current documentation and charter;
3. package namespace and lockfile;
4. CLI/environment compatibility;
5. Pi/runtime names;
6. artifact compatibility;
7. naming governance and verification records.

Do not combine Flow Model Core, another Analyzer, a new host adapter or public package publication into the rename checkpoints.
